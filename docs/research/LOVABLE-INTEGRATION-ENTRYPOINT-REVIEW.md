## 2. Framework: what exists
- `SoftWriters.IntegrationsClient.Ltc.dll` / `SoftWriters.FrameworkEcm.IntegrationService.Ltc.dll`: WCF named pipe `net.pipe://localhost/FrameworkLTC{FrameworkLtc pid}/Service` (endpoint name "Service"), `NetNamedPipeBinding`, MaxReceivedMessageSize 2147483647. ## 3. Evidence for the slow, partial native capture (`windows/FrameworkDesktop.cs`, prototype 6fed8ca)
Capture: 288 readable, all partial, ~117 nodes in ~1.2 s (`docs/PILOT-CAPTURE-REVIEW-2026-11-16.md`).
1. `Observe` (lines 1078-1143) pays one cross-process call per property access. Per node: Current.IsPassword, ProcessId, IsOffscreen, AutomationId, Name, ClassName, ControlType, IsEnabled, HasKeyboardFocus, FrameworkId, BoundingRectangle (~11), `GetSupportedPatterns()` (1), then `TryGetCurrentPattern` for Value, Toggle, SelectionItem, Grid (4, most fail), then pattern `.Current` reads, then `GetFirstChild` plus one `GetNextSibling` per child. That is roughly 20+ round trips per node, about 10 ms per node, which explains 117 nodes at the 1200 ms cutoff. "partial" is `errors>0 || pending.Count>0`, so hitting the time budget alone makes every sample partial. The same file's `VisibleRows` (lines 373-427) already does this in bulk with `CacheRequest`/`GetUpdatedCache`, `AutomationElementMode.None`.
2. Probable reason Qty/DaysSupply/package/start date never appear: `Observe` line ~1096 does `if (current.IsOffscreen) continue;`, which prunes the whole subtree. `VisibleRows` (comment, lines ~396-400) documents that DevExpress raw layout wrappers can be offscreen while their children are visible. `Observe` also walks only `ControlViewWalker`, whereas `VisibleRows` falls back to the raw view. The control ids it wants (`RxEntryPrescription_QtyEdit`, `RxEntryPrescription_DaysSupplyEdit`) are already in its `known` list, so the tree walk is hiding fields it already knows by name. This is a hypothesis from code, not tested.
3. Cheaper targeted reads: one `FindFirst(TreeScope.Descendants, new PropertyCondition(AutomationIdProperty, id))` per known id with a CacheRequest (Name, AutomationId, ClassName, ControlType, IsOffscreen, IsEnabled, IsValuePatternAvailable, Value.Value) is one round trip per field and does not depend on ancestors being onscreen. Replace `GetSupportedPatterns` and the four failing `TryGetCurrentPattern` calls with cached `IsXxxPatternAvailableProperty` values. Read focus first via the focused element. Risk: a provider may realize virtualized items on search; the "never realize" rule needs a check on a test window.
4. Regex is not the bottleneck: the per-node `Regex.Replace` for the label and ~5 HMACs per node (`hash(...)`) cost microseconds against millisecond-scale UIA calls. Redundant work that does matter: `Read()` fetches `LabeledBy.Current.Name` per control (extra round trips); `Scan` discovery calls `root.Current.ProcessId`/`IsOffscreen` on every top-level desktop window (line ~282-291) instead of using the known process ids; `HashSet` for `known`/`labels` is rebuilt every call (trivial).
5. `DocuTrackQueue` doubles round trips on purpose: the Grid path reads every cell twice via `grid.GetItem` (lines ~1062-1065), and the tree path calls `NamedTreeRow` twice per row, each doing a `FindAll(Children)` (lines ~1011-1013). A single cached snapshot of the DataItem subtree plus comparing the RuntimeId list before and after gives the same stability check with one read.
