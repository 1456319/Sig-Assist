# Framework desktop integration (pilot)

## Daily workflow

1. Extract the complete current ZIP. Start `Start-Iguana-Connector.bat` **inside the same Windows/Citrix session as Framework**. A connector on a local PC cannot inspect fields inside a remote Citrix application.
2. Open the E-Rx in Framework and click **Detect open E-Rx**. Multiple Framework instances can remain open. On first use, bring the Framework window used for E-Rx entry forward before returning to Sig-Assist. Discovery searches frontmost-first and stops at the first entry wizard (or a legacy labelled PON). Sig-Assist remembers that top-level window while the connector stays open. Repeat detections and diagnostic reads address it directly and do not inspect the other Framework instances, even when an unrelated E-Rx is open there. Hidden wizard-page subtrees are also skipped. **Choose entry window** lets you select or switch the window explicitly: click it, then click inside the intended Framework window within eight seconds. The selected window title is displayed. If it closes, is replaced or is minimized, restore it or choose the entry window again; Sig-Assist does not automatically switch to another instance. It reads only as far as needed to find the entry window's PON, scrolling when necessary. Iguana then supplies the source SIG, administration times and other order details; reading them from the desktop is not required. The scan leaves the details where it stopped. Under detection help, the optional **Also position Framework at the SIG/admin-times section** setting scrolls to the bottom and then slowly up until the exact **RxFill Indicator / All Fill Statuses** pair is visible, falling back to the bottom if it cannot read that pair. This is off by default and does not gate lookup or sending. Keep the order open during detection. One exposed PON fills the search automatically. **Two or more PONs within the selected entry window show a warning and a choice of PON to find; they do not disable sending.** Choose the matching patient, drug and order from the results. If no PON is exposed, normal lookup still works.
3. Read the prominent **E-Rx administration times** panel beside the translation. These are exact incoming structured values. An absent time is not inferred. **Copy incoming times** is also available.
4. Correct the final SIG and check its review box. In **Send to Framework**, confirm the intended patient, drug, PON and destination. Click **Send approved SIG to Framework**. For split orders, choose the reviewed order part to send.
5. If the SIG field was not identified automatically, use **Choose Framework SIG field**. Click directly inside the SIG text box in Framework within eight seconds, then return to Sig-Assist. Selection only reads the field; check its displayed current text and click Send separately. Sending with an absent or expired target starts this same selection step.
6. The helper fills that exact field and reads back its text. Verify Framework Preview Sig, administration schedule, quantity and days' supply. **You save the prescription in Framework.** Sig-Assist does not invoke save, submit, dispensing or queue-processing actions.
7. **Transfer administration times** provides an editable times draft with separate technician approval. Choose a times text field in the same way if necessary. Grid/multi-row schedule editors need a screen-specific mapping or manual entry.

## Technician authority

As requested, the technician decides which order receives the approved text. A different or multiple detected PON is a warning, not a sending lock. Missing accessible patient/facility/drug metadata does not prevent transfer. A changed destination's current contents may be replaced by the approved text; a warning reports that change. The application still requires review of the exact current SIG, respect for saved exclusions/cancellation/source revisions, and explicit destination confirmation.

Technical failures still need correction: a closed/replaced window, a removed control, an inaccessible/read-only field or a different Windows session cannot accept a transfer. These are not order-identity vetoes. The helper never sends keystrokes or pastes into an arbitrary focused window. A technician-selected field is bound by process start time, window and control runtime ID. An uncertain write/read-back result is reported without automatic retry or rollback.

## Installer findings and compatibility

The Framework 3.3.363 installer was inspected statically; no vendor application code was executed. Its integration assemblies contain `LoadScreen`, `OpenLiteralOrder` and `ProcessQueueMessage`. Those are inbound operations, not a verified selected-order notification or SIG setter. `Vb6ObjectProxy` is an internal bridge. This implementation does not call them.

The managed UI contains `ERxWorkQueueDirectionsView`, its `OrderSigTextBox` and `LinkedSigTextBox`, and `RxEntryView` / `PrescriptionTabDirectionsView`. These names do not establish a public integration contract or prove runtime accessibility. Order/linked-directions editors are not automatically treated as the prescription SIG destination.

The separate .NET Framework helper uses Microsoft's Windows UI Automation. It inspects only `FrameworkLTC` and `SoftWriters.FrameworkLtc` processes in the current session. PON detection accepts exact labels, labelled PON text and paired Title/Value detail rows. Known `ERxWorkQueueWizardView` / `ERxWorkQueueView` controls identify the opened E-Rx; visibility is inherited through the control hierarchy so hidden pages cannot supply stale order data. The visible wizard's `ERxGrid` is read through `GridPattern.GetItem`, with a bounded retry for null cells and `VirtualizedItemPattern.Realize` when supported. Control-view snapshots are refreshed in bulk using UI Automation caching. Empty reads fall back to raw-view snapshots scoped to that same grid, including layout/cell peers omitted from control view. Each scroll settles before reading, with two additional 400ms retries when row text is temporarily unavailable. Grid cells are paired by row/column coordinates, not traversal order. If the provider advertises rows but exposes no children, indexed reads are retried in each viewport after scrolling; a null offscreen cell no longer prevents retrying it when visible. A further bounded fallback uses Windows UI Automation hit testing within the current grid bounds. It requests foreground activation of the selected window once, without clicking or typing. Only cells whose ancestor chain reaches that exact grid are accepted; another window or overlay cannot supply a PON. Bounds are refreshed per viewport to accommodate moves and resizes. If Windows denies activation, use Choose entry window and keep Framework in front until reading finishes.

Scanning stops as soon as a valid labelled PON is found in the selected entry window's grid. Unrelated windows no longer contribute PON candidates or warnings. Multiple PONs exposed within the selected entry window still generate a warning. A successful PON read is not reported as a failure merely because the remaining rows were intentionally skipped. The optional review positioning is separate from PON acquisition, defaults off, and never changes whether lookup or technician-approved sending is available. There is no scroll restoration or restoration warning. No queue rows are selected. Limits are 512 detail rows, 40 pages, a shared 22-second reading budget and up to 30 seconds including optional positioning. The detection/diagnostic helper timeout is 45 seconds; explicit entry-window selection allows 55 seconds including its eight-second countdown. The page allows 65 seconds including first-use compilation. Target selection and sending do not expand or scroll grids.

Automatic destination matching requires exactly one visible, enabled, writable Edit control labelled `SIG`, `Prescription SIG`, or `SIG code` within the open wizard when identified; times use `Administration times` or `Admin times`. The technician's explicit field selection still supports editable text controls in any Framework instance with other labels. Field selection reads only the window containing that focused field, and sending/read-back inspect only the saved destination window. Choosing a send destination does not change the remembered detection window; **Choose entry window** does. Clipboard contents, database rows and OCR are not used.

**Actual Framework screen compatibility needs an on-site check.** Windows tests use synthetic controls to exercise detection, read-back, multiple-PON warnings with sending allowed, edited destinations, read-only controls and explicit target selection. A separate five-process WPF fixture reproduces an open wizard, a triage queue, hidden stale pages, and an 80-row detail grid exposing only 30 rows at once, with its PON at row 67. It tests early stopping at the PON, optional review positioning, provider failures, and continued use of the remembered entry window when another E-Rx opens in a different instance. Diagnostics and sending must ignore that other instance too. Closed/replaced-window tests verify no automatic fallback; a separate native test exercises explicit entry-window selection. Multiple-PON sending within one window remains covered. A 106-row fixture reproduces null indexed cells and delayed rows available only through raw view; separate cases cover visible-only indexed access, cells materialized by point queries in normal/narrow windows, an unrelated same-process overlay, and an empty provider without invented PONs or success claims. These tests do not establish compatibility with every Framework screen or verify its clinical effects. UI Automation is not a transactional vendor API; do not switch orders while sending.

## Diagnostics and setup

If detection or selection fails, keep the relevant Framework screen open and use **Framework detection help → Export desktop diagnostics**. The JSON captures process/window identity and accessible control IDs, parent IDs, depth, labels, types, inherited visibility, values and editability, with scan-limit/error flags. Schema version 5 records the selected top-level window, discovery/remembered/explicit selection mode, and the number of windows actually scanned. It also identifies open-wizard windows and includes detail-grid patterns, advertised row/column counts, initial and collected rows, PON-found/stop reason, null-cell and failure counts, read method, page count, completeness, and optional final review position. Per-viewport diagnostics record the read stage, control/raw/indexed/point method, retry number, elapsed time, scroll position, grid bounds, probe/rejection/null-cell counts, visible row indices, scan-limit flags and bounded control samples, including empty reads. The report also records whether a foreground request was accepted. A failed detection now shows Download PON detection report directly below its status; this downloads the same desktop evidence without another scan. This distinguishes an intentionally incomplete PON-first scan from an accessibility provider that exposes no row text. Password controls are omitted. **The export can contain patient and order text.** It is not uploaded automatically. Share it with which screen was open and which field should receive the SIG; this supplies the runtime evidence for a screen-specific mapping.

The helper is compiled with Windows .NET Framework 4's `csc.exe` into the user's local application-data folder when first needed and cached by source hash. Node invokes it directly. No PowerShell, administrator installation or extra download is used. A missing compiler or an application-control block is reported explicitly. It does not disable or bypass application control; ordinary lookup/copy remains available.

The bridge remembers the entry window separately from field tokens, so the selection survives page reloads and token expiry while that connector process remains running. Its process ID, process start time, top-level native handle and runtime ID are validated before each direct read. A closed/replaced selection remains selected until the technician explicitly chooses another window; no unrelated instance is substituted. Window selectors come from the native helper and stay in server-owned session state. The page supplies only the request to choose a window, not a replacement selector.

The bridge holds short-lived opaque target tokens in memory. They expire after five minutes, are invalidated by a fresh detection/field selection and are consumed before sending. Successful read-back supplies a fresh token. The page cannot replace the saved process/control selectors. Local desktop endpoints require same-origin JSON and grant no cross-origin access.

Iguana access remains `GET /api_query` only. Desktop transfer is a separate local operation. `readOnly` in the legacy health response is explicitly scoped to the Iguana upstream.
